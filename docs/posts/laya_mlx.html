laya-mlx 使用教程

教程
Published

September 21, 2026

整理自原仓库 https://github.com/mizorewww/laya-mlx（Apache-2.0，2.5k stars）+ 上游 Laya 文档 + 本机实测。 核心内容（Python API、CLI predict、Snake、Router、内置预设）都在 Apple M4 / macOS 26 / Python 3.13.11 / MLX 0.32.2 上实测过，输出为真实结果； convert、视频导出和 benchmark 未在本机跑（需要下载额外权重或 ffmpeg），内容来自仓库文档，已标注。

本版精修原则：每个概念按「定义 → 为什么 → 在本实现里对应什么 → 边界与误用」四步讲； 公式给出并逐符号解释；所有数字标注来源（本机实测 / 上游文档 / 第三方）；代码引用一律用函数名而不是行号（行号随版本失效）。

1. 这是什么

laya-mlx 是 Laya「类型化决策模型」（typed decisions）在 Apple 芯片上的本地推理实现：用 MLX 运行，不依赖 PyTorch / Transformers，不联网，不调用云端 API。

「类型化决策」的定义。 调用方用一份材料（state）提出若干道题；每道题声明三件事——题型（choice / score / noul）、题面（instructions）、这道题允许的答案集合（criteria）。模型的工作是：在这道题自己的答案集合上输出一个归一化概率分布，并给出其中概率最大的答案。答案集合是请求时由调用方给定的，不是训练时写死的，所以换一套问题不需要重新训练；但反过来说，模型没有任何能力产生集合之外的答案——它不会写文字，也不会说「以上都不是」，除非你在 criteria 里放了这个选项。

输入输出契约：

内容 形式
输入 state：要判断的材料 字符串 / JSON 对象 / 消息列表（§8.1）
输入 questions：问什么、允许答什么 {问题名: {type, instructions, criteria}}（§8.2）
输出 每道题一个条目 概率分布 + 派生答案 + 置信度（§10）

它不做的事（都是机制决定的，不是没配好）：

  • 不生成文本。 没有自回归解码器，一次前向出结果，output_tokens 恒为 0。
  • 不做开放问答。 答案必须落在一个你给的选项里。
  • 不做多标签。 一道 choice 只返回一个标签；需要「同时判断几件事」就拆成多道 noul 题（§9.1）。
  • 不做检索和推理链。 它只对 state 与你写的题面打分，没有工具、没有外部知识。

三个题型（全部能力就这三种）：

类型 含义 机制 例子
choice 在若干命名选项里单选 在 K 个选项上输出类别分布，返回 argmax 该哪个部门处理？→ billing（p=1.0）
score 在有序等级上打分 在 K 个等级上输出分布，返回期望等级 Σ i·p(i) 多急？→ 1.8694（介于 “soon” 和 “critical” 之间）
noul 判断一个命题真假 伯努利分布，只返回 P(true) 客户要求退款吗？→ 0.9728

和 LLM 的核心区别：

传统 LLM Laya / laya-mlx
生成方式 自回归逐 token 一次前向，0 输出 token
输入 一段 prompt state + 结构化问题定义
输出 自由文本（要解析、可能格式错） 给定选项上的概率分布；结构上不可能出现「格式错误」，错的只可能是判断本身
答案范围 整个世界（可能幻觉） 只有你给的选项
速度 数百 ms–秒 毫秒级（本机 M4 约 7–28 ms/问）
概率的含义 采样随机性，不可信 训练目标（RLCD）按「诚实报概率」给奖励；但发布权重是否校准是另一件事，见 §2.4、§9.3

来源与定位：

它来自上游项目 NandhaKishorM/laya（Convai Innovations 的 Laya 模型家族）。本仓库是独立 MLX 移植：保留模型权重、prompt 格式、温度校准机制和输出 schema，只把推理换成 Apple MLX；训练与微调仍在上游，本仓库不发布新权重。

2. 核心概念与工作原理

这一节把后面各节会用到的概念一次讲清。读完这节，§8（输入）、§10（输出）、§11（参数）都只是查表。

2.1 四个对象：state、questions、criteria、instructions

对象 定义 约束
state 要判断的材料。可以是纯文本、JSON 对象、消息列表 见 §8.1；会被序列化后拼进 prompt
questions 一个字典，key 是问题名（原样回显），value 是一道题的完整定义 见 §8.2 的校验表
instructions 题面。模型读到的就是这句话，它直接参与打分 必须存在；非字符串会被自动转成 JSON
criteria 这道题允许的答案集合 choice/score 必填；noul 可省略。见下

三种题型的 criteria 含义不同：

  • choice：选项标签列表，或 {标签: 说明}。答案空间 = 你写的选项集合——选项没覆盖到的答案，模型只能硬挑一个最接近的，所以官方预设常带 other 兜底。
  • score：有序等级列表，从低到高。顺序即语义顺序，写反了模型学到的顺序感会失效。
  • noul：可以不写；写了就给 {"true": 说明, "false": 说明} 两个选项各加描述。noul 的选项固定是 [false, true] 两个，加不了第三个；想表达「不确定」只能用概率接近 0.5 表达，或者改用 choice 加一个「不确定」选项。

2.2 一次请求在内部长什么样

每道题各自构成一条独立序列，模板是（common.py 的 build_sequence/build_prefix）：

[CLS] <题型> question: <instructions> [SEP] [MASK] 选项0 [MASK] 选项1 ... [SEP] <state> [SEP]

逐段解释：

  • <题型> 是 choice / score / noul 之一；模型带一个 3 类的类型嵌入，同一个问题换个题型是不同的问题。

  • 每个选项前面有一个 [MASK] token，这就是该选项的「打分位」。编码器读完序列后，取每个打分位上的隐状态，过一个打分器（model.py 的 DecisionModel：2 层决策头 + LayerNorm→Linear→GELU→Linear(1)）得到一个实数分数（logit）。

  • 分数只在本题的选项之间做 softmax（题内归一化）。题与题之间互不影响：所以「一次问 7 道题」和「分 7 次问」在判断逻辑上等价，只是合并成一次前向更快。

  • 越界或无效的打分位会被掩成 -1e4（softmax 后约等于 0）。

  • state 在序列末尾只出现一次，但每道题都重复一份。这就是为什么输入的 token 数 ≈ 题数 ×（题头 + state），而不是「所有题共享一份 state」。本机实测（同一段 36 字的 state，含标点）：

    题数 input_tokens
    1 62
    2 125
    3 187
    4 247

    大致每加一道题 +62 token。问 10 道题的成本约是问 1 道的 10 倍——题目要精挑，不要凑数（§9.1）。

2.3 三种题型的数学定义

记这道题有 K 个选项，模型输出的概率分布为 p(0..K−1)：

  • choice：p 是 K 个选项上的类别分布。返回 choice = argmax p，同时给你完整的 probabilities。K=1 时无意义，请至少给两个选项。
  • score：p 是 K 个有序等级上的分布。返回 score = Σ i·p(i)（第 i 级的编号从 0 开始），即期望等级，可以是小数。为什么用期望而不是 argmax：等级之间有序，「0.6 概率在 1 级、0.4 在 2 级」本身就在说「介于 1 和 2 之间」，取 argmax 会把这个信息丢掉。 本机实测量化验证：概率 {0: 0.0302, 1: 0.3601, 2: 0.5186, 3: 0.0911}，手算 Σ i·p(i) = 1.6706，模型返回 score: 1.6705（4 位小数舍入差）。
  • noul：一个伯努利分布，只返回 P(true) ∈ [0,1]；P(false) = 1 − P(true)。判定「是/不是」由你选阈值（不是模型的事），比如 >= 0.5 算「是」。它的选项固定是 false/true 两个，选项描述可省略——所以这是三种题型里唯一不需要你设计答案集合的。

2.4 概率、置信度、校准是三件事

概念 回答的问题 在输出里 会不会被温度缩放影响
概率分布 probabilities 模型在各选项之间怎么分配倾向 每题都有 会
置信度 confidence 这个分布有多集中 每题都有 会
校准 概率值本身可不可信 不单独输出，要自己测 会（校准就是来修它的）

置信度的定义（common.py 的 confidence_from_probs、agent.py）：

  • choice / score：confidence = 1 − H(p) / log(K)，其中 H(p) 是香农熵 −Σ p·log p，K 是选项数。熵越小（分布越尖）置信度越高，取值 [0,1]；K<2 时定义为 1。
  • noul：confidence = max(p, 1−p)。

注意：置信度是分布集中度，不是正确率。模型可以「高置信度地答错」——分布很尖，但尖在错的选项上。§14 里的英文检查点崩坏（Hindi 上 ECE 0.855）就是极端例子。

校准的定义：预测概率与经验正确率是否一致。标准量度是 ECE（期望校准误差）：把预测概率分成若干桶（例如每 0.1 一桶），对每个桶算「桶内平均预测概率」与「桶内实际正确率」之差的绝对值，再按桶内样本占比加权平均。一个校准良好的模型，说自己 80% 把握的那些题里，应该真的约有 80% 答对。

本机检查点的校准状态（重要）：本机 rl_agent_config.json 里 temperature: [1.0, 1.0, 1.0]、temperature_by_options: {}，也就是说这个检查点没有做任何分桶温度缩放，属于「未校准」的发布状态。上游模型卡给出的数据：laya-multilingual 重拟合温度后平均 ECE 从 0.314 降到 0.106。结论：不要把它的概率当频率直接用，除非你按 §9.3 在自己的数据上校准。

2.5 logits → 温度 → softmax

打分器给每个选项一个实数 logit z(i)。出概率的完整链条是：

z(i) --除以温度 T--> z(i)/T --softmax--> p(i)
  • 温度 T 只改分布的尖锐程度：T<1 更尖，T>1 更平。它不改变选项排序，所以 choice/argmax 永远不受温度影响；受影响的只有 probabilities 与 confidence。
  • 本实现按 （题型，选项数）分桶取温度（common.py 的 temp_bucket）：temperature_by_options 里先找形如 "choice:3-5"、"score:11+" 的键（选项数分档：2 / 3–5 / 6–10 / 11+），找不到就用 temperature[题型]。
  • 校准就是「用一批带标注的数据，为每个桶拟合一个 T」，见 §9.3。

2.6 RLCD 与「诚实概率」

RLCD = Reinforcement Learning for Calibrated Decisions，是这个模型家族的核心训练方法。要点：

  • 模型的输出是一组概率；训练时把这份概率交给一个严格适当评分规则（strictly proper scoring rule）——log 损失、球面损失，有序题用 RPS（ranked probability score）——算出奖励。
  • 「严格适当」的数学含义：在期望意义上，只有报出你真实相信的概率分布，才能最大化奖励。任何夸大或压低某个选项的做法，期望收益都更低。
  • 探索时给 logits 加零均值高斯噪声，用组均值基线做 REINFORCE（GRPO 风格）。
  • 因此模型在训练分布上没有动机虚报置信度。

必须分清两件事：训练机制鼓励诚实 ≠ 发布出来的权重已经校准。校准是事后动作（温度缩放），取决于检查点配置和你的数据分布。本机检查点未做（§2.4）。

2.7 token 预算与截断（最容易踩坑的地方）

一条序列有两个长度上限（rl_agent_config.json）：

配置 本机 multilingual 英文检查点 含义
max_len 1024 512 整条序列（题头 + state）的总上限
head_max_len 256 192 题头预算：题型词 + instructions + 全部选项

分配规则（common.py 的 build_prefix，按顺序发生）：

  1. 每个选项文本最多保留 48 token；所有选项先各占一个 [MASK]。
  2. 题头预算减去选项占用后，剩下的给 instructions；不够就先截 instructions。
  3. 如果选项太多导致 opt_budget < 16，每个选项被压到 max(4, (head_max_len − 16) // 选项数) token——选项一多，每个选项只剩三四个 token，语义会糊（§8.5）。
  4. 题头之外的剩余额度给 state；state 超长时，默认保留开头、丢弃结尾（build_sequence 的 truncate_left=False）。

第 4 条有个容易忽略的推论：state 太长时，丢的是结尾。如果你把「最近的对话」放在 state 末尾，超长时最先丢的就是它；想要保住最新内容，得自己先裁剪或调换顺序。

2.8 三个「一次」：一次前向、一次调用、一次批量

  • 一次前向：一批序列同时过编码器和决策头，得到全部题目的分数。计算上是一批矩阵运算，比逐题串行快得多。
  • 一次调用：predict(state, questions) 里的所有题都在这一次前向里算完；内部按 batch_size（默认 16）分块。
  • 一次批量：50 道题一次问，吞吐远高于 50 次 predict（官方 M3 Max 数据：multilingual 50 问 395 q/s；§15）。

注意「一次调用」不等于「共享计算」：state 仍然每题目重复一份（§2.2），节省的是调度与编码器的批处理效率，不是 token 量。

3. 能做什么、不能做什么

适合：

  • 客服工单分派、紧急度打分、退款/流失风险判断
  • 内容审核（垃圾、钓鱼、骚扰、违规严重度）
  • LLM 输入护栏（越狱、提示注入、敏感信息）
  • 大批量文本分类、路由（给大模型选难度/领域）
  • 任何「读一段文字 → 做固定判断」的重复活，且要求快、便宜、离线、概率可用

不适合：

  • 写作、聊天、翻译、总结、代码生成（它根本不生成文本）
  • 开放式问答（答案必须在你给的 criteria 里）
  • 多标签判断（要拆题，见 §9.1）
  • 对精度要求极高的零样本任务（见 §19）

判断标准一句话：你能提前把要判断的问题列穷举、而且这件事要重复做很多次，才适合它。如果每段文字都需要现编不同的问题，说明你需要的其实是 LLM。

VIRTUAL_ENV=.venv uv pip install 'laya-mlx[demo]'
HF_HUB_OFFLINE=0 .venv/bin/hf download aac6fef/laya-multilingual-mlx   # 提前下权重（约 678 MB，含 tokenizer）

方式 C：从 GitHub 源码装

# 或者克隆后开发模式：
gh repo clone mizorewww/laya-mlx && cd laya-mlx && uv sync --extra demo

HF_HUB_OFFLINE 的精确语义

  • HF_HUB_OFFLINE=1：禁止 huggingface_hub 发起任何网络请求，包括每次加载前的「检查模型有没有新版本」。它不影响读取本地缓存，也不影响已下载权重的使用。
  • 本项目所有脚本在 import laya_mlx 之前设置这个变量（os.environ.setdefault），所以加载只走本地缓存，本机实测 0.8–1.1 秒完成。不设时，如果所在网络访问 huggingface.co 受限，每次加载会先卡在版本检查上（本机网络实测 76 秒）。
  • 代价是：离线模式下不能下载新权重。要下新模型就临时加前缀 HF_HUB_OFFLINE=0：
HF_HUB_OFFLINE=0 .venv/bin/hf download <模型名>
  • 如果你在 shell 启动文件里全局设过 HF_HUB_OFFLINE=1，上面的临时覆盖同样适用（环境变量前缀优先）。

6. 三个模型怎么选

检查点（HF ID） 编码器 参数量 上下文 适合
convaiinnovations/laya ModernBERT-large 421M 512 英文文本、护栏、邮件分派
convaiinnovations/laya-multilingual mmBERT-base 322M 1024（最高 8k） 中文等 100+ 语言，最快
convaiinnovations/laya-typed-decisions ModernBERT-large 421M 1024 上游四个 typed-decisions 工作流（微调过）

结构差异（本机 encoder/config.json 实测）：

  • laya-multilingual：mmBERT-base，hidden 768、22 层、12 个注意力头、词表约 256k；每 3 层一个全局注意力，其余层是窗口 128 的局部注意力；位置编码用 RoPE，编码器上限 8192 token（实际 max_len 由检查点配置限制在 1024）。
  • laya / laya-typed-decisions：ModernBERT-large，隐藏维度更大，所以是 421M；上下文默认 512。
  • 参数量差 → 速度差：多语言版是三个里最快的（官方 M3 Max 单问 P50 7.39 ms vs 英文版 13.42 ms）。

底座 vs 微调检查点（选型前必须区分）：

  • laya / laya-multilingual 是底座：上游 typed-decisions 基准上零样本接近随机（0.36 / 0.34，多数类基线 0.461）。它们适合当「可特化的底座」，在你的数据上微调或至少做校准（§9.3）。
  • laya-typed-decisions 是在该基准自己的训练集上微调过的检查点，0.766 的分数属于它；不能把这个数字当作零样本能力，也不能代表你的场景。

8. 输入格式详解

8.1 state：三种写法

# 1) 纯文本
agent.predict("客户说发票被扣了两次，要求退款。", questions)

# 2) 字典（推荐：字段清晰，题面可用反引号点名引用）
agent.predict({
    "from": "user@example.com",
    "subject": "Duplicate charge on invoice #4411",
    "body": "We were billed twice for March...",
}, questions)

# 3) 对话列表（消息列表，适合 agent 轨迹审查）
agent.predict([{"role": "user", "content": "..."}, ...], questions)

行为细节：

  • 字典/列表会被 json.dumps(ensure_ascii=False) 序列化后拼进 prompt（common.py 的 serialize_state）。中文不会被转义成 \uXXXX，字典的 key 顺序会被保留——顺序稳定，意味着 prompt 稳定。
  • 序列模板见 §2.2：state 在最末尾，每道题重复一份。
  • state 里出现的 [MASK] 字面量会被替换成空格（build_sequence）。原因：每个选项前的 [MASK] 是打分位，state 里混进同样的 token 会制造额外的「伪打分位」，污染结果。你自己写 state 文本时不用担心，代码已经处理。
  • state 超长时默认保留开头、丢弃结尾（§2.7）。

8.2 questions：格式与校验规则

questions = {
    "问题名": {          # 随便起，输出时原样带回；一个字典里想问几题都行
        "type": ...,         # 必须：choice / score / noul
        "instructions": ..., # 必须：题面（模型读的就是这句）
        "criteria": ...,     # 看题型（见下表）
    },
}

规则写死在 agent.py 的 Agent._to_internal，违反会直接抛 ValueError：

部分 是否必须 允许的写法
type 必须 "choice" / "score" / "noul"
instructions 必须 字符串；给非字符串会被自动转成 JSON
criteria（choice） 必须 非空列表（字符串、不重复）或非空字典 {标签: 说明}
criteria（score） 必须 非空列表，按从低到高排序
criteria（noul） 可省略 省略，或字典 {"true": 说明, "false": 说明}

三种题型最小写法：

# 单选
{"type": "choice", "instructions": "该谁处理?",
 "criteria": ["财务", "技术", "销售"]}

# 单选 + 每个选项带解释（字典写法，解释会拼进选项文本）
{"type": "choice", "instructions": "该谁处理?",
 "criteria": {"财务": "发票、付款、退款", "技术": "故障、报错", "销售": "报价、新合同"}}

# 打分（顺序 = 语义顺序，从低到高）
{"type": "score", "instructions": "有多急?",
 "criteria": ["不急", "尽快", "很急"]}

# 判断
{"type": "noul", "instructions": "客户是在要求退款吗?"}

# 判断 + 给 true/false 加说明
{"type": "noul", "instructions": "这是钓鱼邮件吗?",
 "criteria": {"true": "诈骗邮件", "false": "正常邮件"}}

渲染细节（common.py 的 render_options、render_criterion）：

  • choice 字典写法的选项文本是 标签: 说明；说明为 None 或空字符串时只渲染标签；0 和 False 是合法说明，不会被吞。
  • score 的选项文本是 level 0: 说明 / level 1: 说明 …，编号从 0 开始，顺序即分数顺序。
  • noul 固定渲染为 false: ... / true: ... 两个选项；省略 criteria 时用默认话术（false: no, the statement does not hold / true: yes, the statement holds）。
  • 说明字段本身可以给结构化数据（dict/list/数字），会被压成 JSON 文本拼进选项（render_criterion）。
  • 选项文本每个最多 48 token；题头总预算见 §2.7。

8.3 反引号引用 state 字段

state 是字典时，题面里用反引号点名要读哪个字段（官方预设全部这么写）：

{"type": "noul",
 "instructions": "Does `message` communicate time pressure or a deadline?"}

先澄清一个常见误解：反引号没有任何解析机制，它就是题面里的普通字符。起作用的方式是文本层面的：message 与 state 的 key 同名，模型在训练数据里见过大量这种写法，于是学会把题面里的这个名字对到 state 的字段上。

因此：题面里写的名字要与你 state 的 key 完全一致（大小写、单复数一致）；state 是纯文本时，反引号只起到「这里是个字段名」的提示作用，没有对应关系可对。

常用字段名（取决于你的 state 结构）：message、body、prompt、post、request。

8.4 一次问多题

一次 predict 里的所有问题共享同一份 state，并在一次前向里批量计算（内部按 batch_size=16 分块）：

result = agent.predict(state, {
    "归谁管": {...}, "急不急": {...}, "要退款": {...}, "有流失风险": {...},
})

两个要点（§2.2 讲过机制，这里是操作含义）：

  • 多问几题不增加调用次数，但每道题都会重复一份 state，token 数近似线性增长。本机实测：1/2/3/4 题 = 62/125/187/247 input tokens。
  • 因此「多问几题」比「多调几次」吞吐高得多；但要克制——每道题都要付一份 state 的钱，只问你真要用的题。

8.5 高级：大选项集与 token 预算

head_max_len（英文默认 192 / 多语言默认 256）是「题面 + 所有选项」的 token 预算。选项超过约 50 个时，每个选项只能分到 3–4 个 token，语义糊掉，准确率明显下降（上游实测 Banking77 的 77 分类：默认设置下 0.425 vs Jev 0.870）。

两种处理方式：

# 方式一：给选项更多空间（改前先验证效果）
agent = laya.load("aac6fef/laya-multilingual-mlx")
agent.cfg["head_max_len"] = 512     # 运行时读取，下一次 predict 生效
agent.cfg["max_len"] = 1024         # 同时保证总长不超过编码器上限

方式二：把大选项集拆成「先粗分类、再细分类」两次调用，每次选项都少而清晰。对绝大多数场景，方式二比硬调预算更稳。

9. 出题与校准

这一节解决两个问题：题目怎么写，以及概率怎么才可信。这两件事决定了这套东西在你手里有没有用——模型只有在你给的选项里选的能力，选项设计错了，再准的模型也救不回来。

9.1 出题规则

  1. 选项集合决定上限。 正确答案不在选项里 = 永远答不对。凡是可能出现的答案都要有归属，包括「以上都不是」——官方预设几乎都带一个兜底项。
  2. 选项要互斥。 语义重叠的选项（「尽快」「很急」）会让模型在两个近义项之间随机分票；写选项时用可区分的具体情景而不是程度副词（见第 4 条的 score 写法）。
  3. choice 选项数量控制在约 20 个以内。 超过会先撞上 token 预算问题（§8.5），不是模型聪明不聪明的问题。
  4. score 的每一级写具体情景，不写抽象程度。 这是官方明确要求，也对：写「对方明显不高兴，但还没翻脸」比写「3 级」信息量大得多。等级从低到高排列，2–10 级。
  5. noul 一个命题只问一件事。 不要写成「客户既要求退款又威胁投诉吗」——两件事同时成立/不成立的概率不是单一命题。另外尽量避免否定句和双重否定，否定式命题是这类模型最容易错的形态之一。
  6. 多标签就拆题。 一道 choice 只能选一个标签；要判断「同时具备哪些属性」，为每个属性写一道 noul，或者拆成多道 choice。
  7. 题面语言用模型训练语言。 英文检查点写英文；multilingual 可以写中文（本教程所有实测都是中文题面）。常见的稳妥组合是：英文题面 + 原始语言内容（内容不要翻译，翻译会引入你自己的理解）。
  8. 题目一旦定稿就别随意改。 原因见下一节。

9.2 措辞敏感性：同一件事，换个问法就换个答案

机制上这很容易理解：题面和选项文本都是模型输入的一部分（§2.2），改一个词就是换了一道题。下面是本机实测。

实验：同一段文字（“快递等了两周，包装还破了个角。客服回得快，但一句道歉都没有，真让人火大。”），同一个命题，四种问法，同一进程内各跑两次：

问法（instructions） P(true)
说话人在表达愤怒或不满吗? 0.7353
说话人对某事感到不满吗? 0.5837
这段文字里有投诉或抱怨吗? 0.7836
说话人有点生气吗? 0.5796

四种问法给出的概率在 0.58–0.78 之间，最高与最低差 0.20。注意它们都在 0.5 以上，所以「阈值 0.5」碰巧给出同一个结论——但生产上阈值常取 0.6 或更高：取 0.6 时，「说话人对某事感到不满吗?」（0.5837）和「说话人有点生气吗?」（0.5796）判「不是」，另外两种判「是」。同一件事、同一份数据，只因为你换了个问法，结论就翻转了。

选项说明（criteria）同样参与判断：同一句问法「这段文字里有投诉或抱怨吗?」——

  • 不写 criteria：0.7836
  • 写 criteria: {"true": "有投诉或抱怨", "false": "没有投诉或抱怨"}：0.8301

可复现性（避免误判为随机性）：

  • 同一批次组合内，连续两次调用结果完全一致（上表数字重复两次不变）。上游验收也是同一口径：「相同输入与批形状下，公开 JSON 完全可重复」（BENCHMARKS.md）。
  • 不同批次组成会有千分位差异：同一道题在 6 题批次里是 0.7845，在 ≤4 题批次里是 0.7836。原因是批内 padding 到不同长度，FP16 的数值舍入路径略有不同。差异在 0.001 量级，不影响结论。

实践含义：

  • 「某个措辞下是 0.83」不等于「事实是 0.83」，只等于「这个问法下的 0.83」。写文案、做审核阈值时，别把单一措辞的数值当客观事实。
  • 校准（下一节）必须在最终定稿的题目上做；改了题面或选项就要重测。
  • 同一个判断最好只用一套措辞做生产，别今天一个问法、明天一个问法，否则阈值没法定。

9.3 校准：让概率变得可用

为什么需要。 本机检查点没有做温度缩放（§2.4），概率可能整体偏尖或偏平；上游数据是重拟合后 ECE 从 0.314 降到 0.106。校准只做一件事：修「概率数值的可信度」，不改「谁排第一」（温度不改变排序，§2.5）。

需要什么。 一批带人工标注的样本，30 条起步，覆盖你的场景、各种难度和各个等级。标注只标你真正关心的维度。

四个指标（先说清楚定义）：

指标 定义 适用
命中率 accuracy argmax 与标注一致的比例 choice
MAE 期望等级与标注等级的差的绝对值平均 score
Brier 概率向量与 one-hot 标注的平方误差平均，越低越好 全部
ECE 分桶后「平均预测概率 vs 实际正确率」的加权平均差（§2.4） 全部

步骤：

  1. 测基线：在标注集上跑一遍，记录命中率/MAE/Brier/ECE。
  2. 拟合温度：按（题型，选项数）分桶，为每桶找一个温度 T（最小化 NLL 或 Brier）。温度只缩放概率，不动排序。
  3. 复测：用同一批数据看 ECE 是否下降；命中率理论上不变（argmax 不变），如果变了，说明实现有问题。
  4. 留出验证：换一批没参与拟合的样本再测一次。校准也可能过拟合。

边界（很重要）：

  • 校准只能修概率的数值，不能把接近随机的排序修对。底座检查点零样本接近随机（§6），那种情况要先微调，再谈校准。
  • noul 的判定阈值应该由你的误判代价决定，不要默认 0.5：漏判代价高就降阈值，误报代价高就升阈值。校准之后才知道 0.3 和 0.7 各意味着什么。
  • 没有标注数据时，把 confidence 当粗排序参考，不要当概率使用。

9.4 出题常见错误清单

症状 原因 解法
某些正确答案永远不被选中 选项集合没覆盖 加选项或加兜底项 other
两个选项概率总是接近 选项语义重叠 给每个选项写可区分的具体情景
score 结果总是中间值 等级描述太抽象 每级改成具体情景，拉大相邻级差异
模型在否定句上表现差 否定式命题难以对齐 改成正向问法（「是 X 吗」而不是「不是 X 吗」）
高选项数时准确率骤降 撞上题头 token 预算 拆分选项集或调大预算（§8.5）
上线后阈值时灵时不灵 改过题面/选项 题目定稿后冻结，改了就重新校准（§9.2）

10. 输出格式详解

顶层结构：

{
  "model": "laya-rl-agent",
  "answers": { 每道题一个条目，key = 你传入的问题名 },
  "usage": {"input_tokens": N, "output_tokens": 0},
}

每个答案的公共字段：

字段 含义
type 题型（回显）
confidence 分布集中度，不是正确率。choice/score：1 − H(p)/log K；noul：max(p, 1−p)（§2.4）
action.act_probability 独立的动作头输出，见下
probabilities 该题的完整概率分布，保留 4 位小数

action.act_probability 的完整定义（model.py 的 DecisionModel）：

它来自一个和答案打分器并列的头：输入 = [CLS] 的隐状态 + 4 个统计特征（top-1 概率、top-1 与 top-2 的差值、归一化熵、选项数/255），过一个两层 MLP（Linear(768+4→256) → GELU → Linear(256→类数)），输出类数 = len(act_costs)+1。本机检查点 act_costs = {"escalate": 0.5} → 共 2 类；公开字段给的是 softmax 之后第 0 类的概率，即 P(act)：「直接作答」相对「升级处理」的估计。

它不是「模型有多确定」，也别拿它当质量分数；它是上游为 agent 场景保留的动作决策字段，普通分类任务里可以忽略。

三种题型各自的字段：

题型 特有字段 说明
choice choice + probabilities{标签: 概率} choice = 概率最大的标签
score score + legend{编号: 等级名} + probabilities{编号: 概率} score 是期望等级 Σ i·p(i)（§2.3）；legend 的 key 是字符串数字
noul noul P(命题为真)

两个容易引起困惑的显示细节：

  1. probabilities 合计不一定正好 1。 每项先各自四舍五入到 4 位小数再返回，所以合计可能是 99.99% 或 100.01%。本机实测例：{"开心": 0.02, "生气": 0.4874, "难过": 0.4425, "焦虑": 0.0135, "惊讶": 0.0144, "中性": 0.0223}，合计 1.0001。这是舍入，不是概率没归一化——内部 softmax 严格归一到 1。
  2. usage.input_tokens 是各题序列长度之和，不是在说「你的 state 有多长」。同一份 state，1/2/3/4 题分别是 62/125/187/247 tokens（§2.2 实测）。output_tokens 恒为 0。

11. 加载与推理参数全解

agent = laya.load(
    "aac6fef/laya-multilingual-mlx",  # 位置参数：HF ID 或本地目录
    device=None,        # None=MLX 默认；"gpu"/"metal" 或 "cpu"
    token=None,         # HF token（私有仓库/限流用；也可用 HF_TOKEN 环境变量）
    subfolder=None,     # 从打包仓库取子目录，如 "multilingual"
    dtype="float16",    # float16 / float32 / bfloat16
    revision=None,      # 固定 HF 版本（可复现）
    batch_size=16,      # 每次前向的问题数上限，超出自动分块
    compile=False,      # mx.compile 编译计算图（首次有编译开销）
    pad_to_multiple=None,  # 如 16：把序列长度补齐到 16 的倍数
    cache_prompts=False,   # 启用有界前缀缓存（≤128 题）
)

逐参数说明（默认值 / 取值 / 作用 / 什么时候改）：

  • dtype：权重与计算精度。默认 "float16"（2 字节/参数，快且省内存）。需要和上游 PyTorch 数值对齐时用 "float32"；"bfloat16" 可以传但不在发布验证矩阵里，遇到异常先换回 fp16/fp32。

  • batch_size：一次前向最多装几道题，超出自动切块。默认 16 是内存与吞吐的折中；官方测 50 题吞吐时用 64。题多、内存够就调大。

  • compile：用 mx.compile 把计算图编译起来，减少逐次调度开销。代价：首次调用有编译时间，且编译结果按输入形状特化——换了序列长度就可能重新编译。

  • pad_to_multiple：把序列长度补齐到某个倍数（如 16）。作用是减少形状种类，让 compile 的编译结果能覆盖更多批次；单独用没有意义。

  • cache_prompts：启用有界前缀缓存（prepared.py 的 PrefixCache，LRU 上限 128）。它缓存的是题目本身的 token 化前缀（题型 + 题面 + 选项 + 题头预算，作为 key），不缓存编码器输出、也不缓存预测。适合「同一批固定题目、不断换 state」的循环：题目前缀只 tokenize 一次，每次只重新编码 state。

  • device：None 用 MLX 默认（Apple GPU / Metal）；"cpu" 强制 CPU（调试用，慢）。

  • subfolder：convaiinnovations/laya 这个仓库打包了三个检查点，只下载你要的子目录：

    agent = laya.load("convaiinnovations/laya", subfolder="multilingual")

  • revision：锁定 HF 版本，保证可复现：

    agent = laya.load("convaiinnovations/laya",
                  revision="c5d78730f3493e4fe16d61507ef4b78eef7318cf")

  • token：私有仓库或触发限流时用；也可以设环境变量 HF_TOKEN。

  • 等价别名：agent.predict(...) 与 agent.system_one(...) 完全等价（agent.py 的 predict = system_one）。

  • 运行时改预算：head_max_len / max_len 是每次 predict 时从 agent.cfg 读的，所以可以在加载后修改（见 §8.5）；但这属于改了推理条件，改前先验证效果。

三个优化开关（compile / pad_to_multiple / cache_prompts）默认全关，联用是官方验证过的路径（Snake 场景约 +6.5%）。因为首次有编译开销、形状特化，短任务不一定划算，务必自己 A/B 后再上生产。

14. Router：多语言自动路由

Router 解决的问题：三个检查点的语言能力不同，英文检查点遇到非拉丁文字不是变差，而是高置信度答错（上游数据：20 选项的 MASSIVE intent 上 Hindi 0.100、Korean 0.103，随机是 0.050；Hindi 上 ECE 0.855——它错得很自信）。所以路由的第一信号是书写系统检测，而不是语种识别。

检测与判定规则（router.py 的 route，lang.py 的 analyse）：

检测结果 路由到 理由文本（真实输出）
state 里没有字母（script: unknown） default（默认 english） no letters detected in state; using default
非拉丁书写系统（如 han） multilingual non-Latin script (...); the English checkpoint cannot read it
拉丁字母但判定不是英文 multilingual Latin script but language looks like ..., not English
英文 english English Latin text 
from laya_mlx import Router

# {'model': 'multilingual', 'repo': 'convaiinnovations/laya/multilingual',
#  'reason': 'non-Latin script (han, 100% of letters); ...', 'detection': {...}}

路由优先级（route 的判定顺序）：显式 model > 显式 task > 工作流检测（需 auto_task_detection=True）> 显式 lang > 脚本/语言检测 > 默认（english）。

routing 字段（RouteDecision）：model（选了谁）、repo（对应仓库/子目录）、reason（为什么，可直接展示给用户）、detection（检测明细，显式指定时为 None）、workflow（命中的 typed-decisions 工作流名）。

构造参数：

Router(
    models=None,              # 覆盖模型映射（值可为 "repo" 或 ("repo", "subfolder")）

    auto_task_detection=False,# 按 question id 集合自动选 typed-decisions 工作流
    standalone_repos=False,   # 用独立 HF 仓库而非打包仓库
    preload=False,            # 预先加载全部（服务器/演示推荐）

)

模型名别名（router.py 的 normalise_name）：en / laya / default → english；multi / ml / laya-multilingual → multilingual；typed / typed_decisions / typed-decisions / laya-typed-decisions / decisions → typed-decisions。

typed-decisions 的四个工作流（auto_task_detection=True 时启用，按问题 id 集合的精确匹配触发，详见 router.py 的 _TYPED_DECISION_WORKFLOWS）：

工作流 问题 id 集合
invoice_processing discrepancy_severity, disposition, duplicate, matches_order, urgency
security_incidents credential_compromise, disposition, severity, true_positive, urgency

加载与内存管理：

  • 默认 max_loaded=1：语言来回切换时每次都要重建模型（官方数据：冷载 7–10 秒，CPU 中位数 7.4 s / T4 10.3 s）。检测本身只要微秒级，重建才是成本。
  • 服务/演示场景用 Router(preload=True) 或 router.preload(["english", "multilingual"])，把加载成本前置。
  • 已有 Agent 可以 router.attach("english", agent) 复用，避免重复占内存；router.unload() 释放。
  • 默认映射从打包仓库 convaiinnovations/laya 按需下载（首次路由到某模型时下 0.6–0.8 GB）。如果已经缓存了 aac6fef/*-mlx 的权重，用 Router(models={"multilingual": "aac6fef/laya-multilingual-mlx"}) 覆盖映射，避免重复下载。

调优建议（按收益排序）

  1. 多题一次调用：所有问题共享一次批量前向，比循环调用快得多（但记住 token 成本仍随题数线性增长，§2.2）。
  2. batch_size 调大（如 64）：批吞吐显著上升，注意内存。
  3. compile=True + pad_to_multiple=16 + cache_prompts=True：官方验证过，Snake 场景约 +6.5%，但首次编译有成本（§11）。
  4. dtype="float16"（默认）：速度/内存最优；只在需要数值对齐时换 float32。
  5. 减少无用上下文：state 越短越快；超长时默认丢结尾，别把关键内容放在会被丢掉的位置（§2.7）。

官方明说：没有找到「同权重再快 10 倍」的方法，实测部分场景仅 1.03–1.08×（见 docs/ENGINEERING_10X_RESEARCH.md）。

17. Snake 终端游戏完全说明

Snake 是这套模型最直观的演示：每一步，模型回答三个真实问题——

问题 题型 选项/命题
下一步走哪 choice 四个方向（up/down/left/right）
前方有安全路线吗 noul 命题：存在安全的前进路线
食物现在可达吗 noul 命题：食物能通过当前空格到达

17.1 三个先讲清楚的概念

  • legal / safe 是两回事（game.py 的 game.moves()）：
    • legal：这一步不会撞墙、不会撞到自己；
    • safe：这一步走完后，蛇不会被自己困死（满足「循环安全」判据）；
    • 模型只看得到你写进 state 和选项描述的信息，所以选项描述里会写明「Blocked / Unsafe / Safe」，让它有依据。
  • 安全盾（shield）：默认开启。模型给出 move 题的概率后，取 proposed = argmax(概率)；如果 proposed 不是 safe 动作，就改选 safe 集合里概率最大的动作。此时界面标记 SHIELD，记录里 intervened = true。模型自己的概率不会被改写，只是执行时被拦一下。用 --unassisted 关掉安全盾，直接执行模型原始 top-1（观察模型原始行为时用）。
  • 两个 noul 的用法：dead_end_risk = 1 − P(risk 题)，food_reachable = P(food 题)。它们是模型对局面的事实判断，不是校准过的死亡概率——面板上展示时要知道这一点。

--prompt 有 compact（默认）和 detailed 两档：detailed 给完整局面描述（可用安全方向数、空格数、蛇长、食物可达性）和更细的选项说明；compact 只给「有无安全路线 / 食物是否可达」两句要点和更短的选项。两档会得到不同的概率分布——这就是 §9.2 说的「题面/选项是输入的一部分」在游戏里的体现。

--optimize = 编译 + 长度按 16 分桶 + 有界前缀复用，三件一起开（§11）。

19. 限制与诚实声明

上游和移植方都反复强调的几点，选型前务必知道：

  1. 基础检查点是「可特化的底座」，不是零样本神器。 在上游 typed-decisions 基准上，未微调的 laya / laya-multilingual 接近随机（0.36 / 0.34，多数类基线 0.461）；0.766 的分数属于在该基准训练集上微调过的 laya-typed-decisions 检查点（§6）。
  2. 高基数选项是弱项：>20–50 个选项时准确率下降明显（token 预算问题，§8.5）。
  3. score 是最弱的题型（上游 SST-5 举例 0.372）；等级集换新的也容易掉。
  4. 概率 ≠ 准确率。 confidence 是分布集中度；本机检查点未做温度缩放（§2.4），OOD 数据上会过度自信。要当概率用，先按 §9.3 校准。
  5. 答案空间 100% 由你的选项决定。 选项没覆盖的答案，它只能挑最接近的；题目设计的重要性不低于模型选择（§9.1）。
  6. 英文检查点只有英文；multilingual 覆盖 100+ 语言但也不是句句准，非拉丁文字必须走 multilingual（§14）。
  7. 不可生成文本：没有自回归解码器，也没有工具、检索或多轮记忆；一次前向就是全部。
  8. 移植保真 ≠ 模型正确：63/63 是「和上游数值一致」，不是「答案对」。
  9. 性能数据是单机单次测量（官方 M3 Max），不构成跨设备/生产耐久承诺。
  10. 训练机制 ≠ 发布校准：RLCD 让模型在训练分布上「诚实」；发布权重是否校准、在你的数据上准不准，都要单独验证（§2.6、§9.3）。

20. 和上游 Laya、Jev 的关系

  • TypeSafe Jev：这个品类的开创者（闭源 API，「System One Model」），强在高基数选项和软分布匹配。第三方实测延迟 236–276 ms/问。
  • Laya（Convai Innovations，NandhaKishorM/laya）：开源权重（Apache-2.0）的同形态模型，官方宣称单问快 6–8×、多语言 45/51 可用、重拟合温度后 ECE 0.081 vs Jev 0.246；Jev 在 >20 选项仍领先。
  • laya-mlx（本项目）：Laya 的 MLX 推理移植，绑定上游 commit 6a5819129eb220570792e417e49723d697efd76f，非 Convai 官方发布；RLCD 训练和微调仍在上游。
  • open-jev（Kotoba Labs）：独立复现「Jev 形态」的另一个开源模型（DeBERTa-v3-large），和 Laya 无关但同一路数。

数字的来源与可比性（重要）：

  • 上表中 Laya 一侧的数字来自 Laya 官方模型卡（自家基准、自家口径）；Jev 一侧是第三方公布的数据，两侧样本、题面、评测条件并不相同。
  • 因此这些对比只能说明「同一量级、各有胜负」，不能当成严格的同条件对拍。
  • 唯一可以自己验证的是本机数据（§15 的 M4 实测），以及你自己标注集上的结果。
