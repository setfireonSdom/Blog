Agent 和 Harness 到底有什么区别？

面向读者的 AI Agent 基础科普

调研日期：2026-08-29

说明：agent harness 尚无全行业统一定义。本文综合 Anthropic、OpenAI、LangChain、MCP 等官方资料，采用一套便于理解和讨论的工作性定义。产品功能和内置角色变化很快，具体情况以各产品最新文档为准。

先说结论

Agent 是执行任务的主体，Harness 是让这个主体能够持续、可控地工作的外层系统。 本文知道业界也常把整套应用称为 Agent，但为了把各层讲清楚，下文会把执行体和外层设施分开讨论。

再说得具体一点：

  • 模型（model)负责根据当前信息判断下一步，例如“先搜索报错位置”。
  • Agent围绕目标反复进行“判断、行动、观察”，直到完成任务或必须停下。
  • Harness准备模型需要的上下文，提供工具，执行工具调用，保存状态，控制权限，并管理整个循环。

可以把模型想成发动机，把 Agent 想成正在开车完成任务的司机，把 Harness 想成汽车本身及其控制系统。发动机提供动力，司机决定往哪里走；方向盘、刹车、仪表、导航和安全限制，则让这趟行程真正可行。

这个类比并不严格，但足以解释一个常见误会：能力很强的模型不等于好用的 Agent。同一个模型放进不同的 Harness，能看到的资料、可用的工具、犯错后的恢复能力都可能不同，最终表现自然也会不同。

一个 Agent 是怎样完成任务的

假设你对一个编程工具说：

修复登录接口偶尔返回 500 的问题，并运行测试。

一次典型执行大致如下：

  1. Harness 收到任务，读取项目规则、当前会话和允许使用的工具。
  2. 模型看到这些信息，判断应该先搜索登录接口和错误处理代码。
  3. 模型生成一个结构化的工具请求，例如调用代码搜索工具。
  4. Harness 检查工具是否存在、参数是否正确、操作是否越权，然后真正执行搜索。
  5. 搜索结果作为新的“观察”返回给模型。
  6. 模型根据结果决定读取文件、编写复现测试、修改代码或继续调查。
  7. Harness 依次执行这些操作，记录状态，并在危险操作前请求批准。
  8. 测试通过后，Agent 输出修改说明；如果工具持续失败、权限不足或达到轮数上限，Harness 会让任务停止。

整个过程可以压缩成一个循环：

目标
  ↓
模型判断下一步
  ↓
请求调用工具
  ↓
Harness 检查并执行
  ↓
环境返回结果
  ↓
Harness 更新上下文和状态
  ↺ 继续判断，直到完成或停止

模型通常不会亲自读取磁盘、运行命令或访问数据库。它生成工具名和参数，真正的执行由 Harness、本地程序或外部服务完成。因此，“模型调用了工具”是方便交流的简称，更严谨的说法是：模型选择并请求调用工具，Harness 验证和执行调用，再把结果交还模型。

Agent 是什么

Agent 原本就是人工智能里的老概念，并非大模型时代才出现。传统定义强调两件事：感知环境，以及对环境采取行动。《AI Agents That Matter》将传统 AI 中的 Agent 概括为“能够感知环境并对环境采取行动的实体”。照这个宽泛定义，机器人、游戏角色甚至简单控制器都可能算 Agent。

今天人们谈论的通常是 LLM Agent，即以大语言模型（Large Language Model，简称 LLM）作为动态决策组件的 Agent。Anthropic 在《Building effective agents》中给出了一条很实用的分界：

  • Workflow 通过预先写好的代码路径组织模型和工具。
  • Agent 则由模型动态决定过程和工具用法，对“怎样完成任务”保有一定控制权。

据此，本文采用下面的定义：

在本文的产品分层中，LLM Agent 指由模型驱动、围绕目标持续观察状态、选择行动并接收反馈的执行体；负责承载和控制这一过程的外层设施称为 Harness。

这个定义里有三个关键词。

第一，目标。 Agent 不是漫无目的地生成文字，而是要完成某件事，例如订票、整理资料或修复软件缺陷。

第二，反馈。 Agent 会看到工具结果、测试报错或用户补充的信息，而不是只根据最初的一句话回答一次。

第三，循环。 Agent 根据新情况继续选择下一步。工具不是逻辑上的绝对必要条件，但现实中的 Agent 通常需要工具才能影响外部世界。

Agent 也不一定“完全自主”。有些 Agent 可以连续工作很久，有些每次修改文件都要用户批准。Agent 的自主程度有高有低，并不存在非黑即白的统一门槛。

这里还有一个容易纠结的细节：Agent Loop（Agent 循环）在概念上描述 Agent 反复“判断、行动、观察”的行为，在工程上则通常由 Harness 实现和控制。

Harness 是什么

Harness 原意是挽具、安全带或线束。放在软件语境里，它表示一套包在核心组件外面、负责连接和控制的设施。测试领域早就有 test harness，即负责准备环境、运行测试和收集结果的一套测试执行与控制设施。

Agent harness 至今没有一份所有厂商都遵循的标准定义。Anthropic 将 Claude Agent SDK 称为一种通用 Agent Harness，并特别提到工具使用、上下文管理和压缩等能力。LangChain 的产品分层文档则把 Harness 描述为“带有明确取舍、开箱即用”的框架，常见能力包括规划、子 Agent、文件系统和 token 管理。Token 是模型处理文本时使用的基本计量单位，一个汉字、词或标点可能对应一个或多个 token。

本文采用下面的工作性定义：

Agent Harness 是围绕模型搭建的执行与控制层。它把提示词、工具、上下文、状态和 Agent 循环组装起来，并负责权限、停止条件、错误恢复与运行记录，使 Agent 能够真正持续工作。

一套 Harness 可能包含以下能力，具体组合因产品而异：

能力 具体做什么
上下文组装 把用户任务、系统规则、项目资料和工具说明整理后交给模型
Agent 循环 在“模型判断、工具执行、结果回填”之间反复运行
工具调度 校验参数，调用文件、终端、浏览器、搜索或外部 API（应用程序接口）
权限控制 决定哪些操作允许、拒绝或必须先询问用户
状态管理 保存任务进度、文件变化、会话记忆和待办事项
上下文压缩 对过长历史做摘要、裁剪或按需检索，避免超出上下文窗口
错误恢复 处理工具失败、超时、进程中断和重复循环
停止条件 在任务完成、达到轮数上限、超出预算或遭遇阻塞时停下
可观测性 保存日志、轨迹、耗时和成本，便于调试与评估
多 Agent 调度（可选） 把子任务交给不同 Agent，并汇总它们的结果

Anthropic 对长时间运行 Agent 的实验很能说明问题：即使模型和工具不变，只要 Harness 让不同会话通过进度文件、Git 版本记录、功能清单和测试结果交接，Agent 就更不容易重复劳动、半途丢失状态或过早宣布完成。

两者的边界为什么总是说不清

因为 Agent 这个词经常同时指三种不同的东西：

  1. 架构概念：会观察、决策和行动的系统。
  2. 运行实例：眼下正在处理某个任务的一次 Agent 会话。
  3. 商品名称：厂商口中的“Coding Agent”或“Research Agent”产品。

一个完整产品也可能同时跨越多层。Claude Code、OpenCode 和 Codex CLI 都可以被市场称为 Coding Agent；但从软件架构看，它们又提供界面、工具、权限、上下文和执行循环，因此整个产品也可视作 Harness。产品里面再配置 Explore、Plan 或 Reviewer 等具体 Agent。

所以，“Claude Code 是 Agent 还是 Harness？”没有唯一答案：

  • 指整个软件产品时，它是一套 Coding Agent 产品，也承担 Harness 的职责。
  • 指产品里正在完成任务的执行体时，那是 Agent。
  • 指 Claude Sonnet、Opus 等负责生成下一步的组件时，那是模型。

这不是故意玩文字游戏，而是观察层级不同。遇到模糊宣传时，与其追问它到底“算不算 Agent”，不如看四件事：谁决定下一步、谁执行工具、谁保存状态、谁控制权限。

不要再混淆这些术语

Model：模型

模型是接收输入并生成输出的参数化计算组件。在 Agent 系统中，它通常负责理解信息、推理并提出下一步，但不会天然获得磁盘、浏览器或数据库权限。

推荐说法是“这个 Agent 使用某模型作为决策核心”，而不是“这个模型自己打开终端改了文件”。

Tool：工具

Tool 是暴露给 Agent 的可调用能力，通常有名称、说明、输入参数和返回结果。例如读取文件、搜索网页、运行测试、查询数据库和操作浏览器。Tool 也可以调用外部 API，与其他软件交换数据或请求服务。

工具解决的是“能做什么动作”。模型选择动作，Harness 或工具服务执行动作。

MCP：工具和上下文的连接协议

MCP 全称 Model Context Protocol，中文常译为“模型上下文协议”。它采用客户端与服务器结构，让 AI 应用发现和访问外部的工具、资源与提示模板。

根据 MCP 官方架构文档，MCP 只规定上下文怎样交换，不规定应用怎样使用模型或管理上下文。因此：

  • MCP 不是 Agent。
  • MCP Server 也不必是 Agent。
  • Tool 可以不通过 MCP 提供。
  • MCP Server 可以一次提供多个 Tool，也可以提供只读资源和提示模板。

更完整的说法是：“AI 应用中的 MCP Client（客户端）连接 MCP Server（服务器），获取其工具、资源或提示模板；Harness 再按需把这些能力纳入 Agent 的上下文和可用工具。”

Skill：供 Agent 使用的任务知识或操作规程

Skill 并无全行业统一格式。本文以下专指 Agent Skills 规范中的 Skill：它至少是一个包含 SKILL.md 的目录，还可附带脚本、参考资料和模板。它主要教 Agent “遇到这类任务应该怎么做”。

Tool 和 Skill 的区别可以概括为：

  • Tool 解决“可以执行什么动作”。
  • Skill 解决“这类工作应该按照什么方法完成”。

例如，终端是 Tool；一份要求“先复现故障，再修改代码，最后运行测试”的调试规程则是 Skill。

Workflow：预先规定路径的流程

Workflow 的主要步骤和分支由开发者提前写好。例如，发票处理系统固定执行“识别内容、校验金额、人工审批、写入财务系统”。流程中可以调用模型，但模型通常不能任意改变总体路径。

Agent 与 Workflow 可以混用。探索和修复代码可以由 Agent 动态决定，测试、审查和发布门禁则适合使用确定性 Workflow。

Framework、Runtime 和 Scaffold

这三个词也经常重叠。为了方便讨论，可以这样区分：

  • Framework（框架）提供构建 Agent 的通用抽象，例如模型接口、工具封装、消息类型和 Agent 循环。
  • Runtime（运行时）承载实际执行，通常负责生命周期和调度，并可能提供持久化、暂停恢复与并发能力。
  • Scaffold（脚手架）多见于论文和评测，泛指围绕基础模型搭建的提示、工具接口、循环和重试结构。

Harness 往往比 Framework 更“有主见”：它不只提供零件，还预先选好常用工具、提示、子 Agent 和上下文策略。但这只是工作性区分，不同项目完全可能同时自称 Framework、Runtime 和 Harness。

常见的 Agent 有哪些

Agent 可以按任务角色分类。下面这些名称不是统一标准，而是常见的职责划分：

Agent 类型 主要职责
Coding / Builder Agent 修改代码、实现功能、运行构建和测试
Explore Agent 只读搜索代码库，定位文件、依赖和调用关系
Planner Agent 分析目标、拆解任务并提出执行顺序
Reviewer Agent 审查代码或文档，寻找错误、风险和遗漏
Test Agent 复现故障、设计测试并核对结果
Research Agent 检索资料、核对来源并整理结论
Browser Agent 操作网页，填写表单或完成跨页面任务
Data Agent 查询数据库、运行分析并生成报告
Orchestrator Agent 拆分任务、调度其他 Agent 并汇总结果
Customer Support Agent 查询用户和订单信息，处理客服问题

一个角色名称不一定代表一个完全独立的 Agent。有些产品只是切换系统提示词、模型或权限；有些会创建拥有独立上下文和生命周期的子 Agent；还有些只是让同一个 Agent 进入不同模式。

以 OpenCode 为例，其官方文档把 Build 和 Plan 列为主 Agent，把 General、Explore 和 Scout 列为子 Agent：

  • Build 可以使用完整开发工具，适合真正修改项目。
  • Plan 默认限制写文件和终端操作，适合分析与规划。
  • Explore 是只读代码库探索 Agent。
  • Scout 用于外部文档和依赖研究。

这里的 Agent 本质上是不同的模型、提示词、工具权限和运行方式的组合。OpenCode 本身则提供承载它们的 Harness。

判断一个东西属于哪一层

看到新产品或新术语时，可以按下面的问题判断：

判断问题 承担该职责的组件通常属于
谁根据当前情况决定下一步？ Model 或 Agent
谁围绕目标持续进行“判断－行动－观察”？ Agent
谁真正读取文件、调用 API 或运行命令？ Tool、工具服务或 Runtime
谁准备上下文、执行工具并控制权限？ Harness
谁规定固定步骤和分支？ Workflow
谁提供开发用的通用抽象？ Framework / SDK
谁负责持久运行、暂停恢复和调度？ Runtime
谁负责连接外部工具与资源？ MCP 等协议或集成层
谁教 Agent 按什么方法处理一类任务？ Skill

真实产品往往横跨几层，这张表的目的不是强行给产品贴唯一标签，而是弄清每一部分实际负责什么。

为什么 Harness 越来越重要

早期讨论常把 Agent 成败归因于模型够不够聪明。实际应用很快暴露出另一面：模型可能会选错工具、忘记目标、重复尝试、在长任务中丢失状态，或者未经验证就宣布完成。

Harness 正是在处理这些“把一次聪明回答变成可靠工作过程”的问题：

  • 好的工具说明能减少参数错误。
  • 合理的权限系统能阻止危险操作。
  • 测试和环境反馈能让 Agent 发现自己做错了。
  • 状态持久化能让长任务跨会话继续。
  • 上下文压缩和按需检索能降低信息过载。
  • 固定的发布门禁能避免把高风险步骤交给模型自由决定。

因此，评估一个 Agent 产品不能只看它用了哪个模型。还要看它给模型配了什么工具、怎样组织上下文、如何验证结果、出了错能否恢复，以及用户能否看见和控制它的行动。

最后记住这张关系图

用户界面 / 产品
└── Agent Harness
    ├── Agent
    │   ├── Model
    │   ├── Instructions
    │   └── Agent loop
    ├── Tools
    ├── Skills
    ├── Context and state
    ├── Permissions and guardrails
    ├── Runtime
    └── MCP and other integrations

它不是所有系统都必须遵守的标准分层，但足以应付大多数讨论：

模型提供判断能力，Agent 围绕目标作出连续决策，Harness 则把模型、工具、上下文和控制机制组装成一个真正能工作的系统。

以后再看到某家公司宣传“全新 Agent”，先别急着被名字带着走。看看它究竟换了模型，增加了角色，接入了工具，还是改进了 Harness。把这几层拆开，绝大多数概念都会清楚很多。
